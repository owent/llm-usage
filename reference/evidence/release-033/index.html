0.3.3 local data repairs

Date: 2026-10-19. Application/npm/Cargo/Tauri versions are 0.3.3. No dependency ranges changed; the pnpm lock has no project-version field. Work covers three reported symptoms, using read-only local Agent sources and independent copies of the statistics database. No original Agent files or live statistics were rewritten, and no new model requests were made.

Trends: three records requiring review

All three were Codex codex-rollout-5 records from native version 0.163.0. A child rollout’s second-line compacted.payload.latest_token_usage_record carried another thread’s response. The old reader assigned the child session, the compaction time and no model. The owning thread contained the same response ID and identical usage, with its original time and codex-auto-review model. Reading both created three ownership/model conflicts.

Record Input including cache Cache read Output Reasoning subset Total
1 174,049 169,728 72 14 174,121
2 66,172 63,232 78 19 66,250
3 162,642 160,512 76 8 162,718

Parser 6 excludes foreign-thread carries from new calls. Recovery requires the complete old event digest reconstructed from that carry and a matching native owner response, with identical usage, quality and revision. It corrects ownership/model/time transactionally, preserving original observation time and diagnostics. Distinct native candidates survive separate scan windows so later matching data cannot erase a real contradiction.

The final consistent old-database copy started with 11,208 Codex events and three conflicts. Three passes processed 136 existing source files; the first stopped at the bounded file window, and the second completed. All three false conflicts became zero. Every preexisting event remained; changes to all eight token fields, quality, cost, creation time and observation time were zero. Three old update_conflict diagnostics remain, alongside three inherited_compaction_corrected entries. The scan also collected 240 newer Codex records from active local sessions; these are separate from the three ownership corrections.

Source notices

The initial database had 18 Codex files and one Kilo file marked active_compat, with otherwise normal source health. A version not listed in the exact registry alone no longer causes a compatibility badge when the expected record structure is valid and complete. Internal versions, parser references and compatibility diagnostics remain. Malformed records, missing required ownership and unsupported formats still produce concrete notices.

“Source files cleaned up” was based only on a recorded path not existing. The initial snapshot contained 354 missing Codex paths and one missing VS Code Copilot path; this does not prove which program moved or deleted them. At the user’s request the label now says “Source files cleaned up or archived”, in all ten languages. Its tooltip explains the observed missing path without attributing deletion to an Agent. Access-check errors are no longer classified as missing paths. Collected history remains subject to retention; missing originals and uncollected content cannot be recovered by rescanning. Keep a statistics backup before clearing data.

Oversized Codex records

The 2026-10-22 read-only check reproduced one degraded Codex file, with native cli_version=0.163.0-alpha.11 and a retained line_too_long diagnostic. Three response_item/custom_tool_call_output lines were 10,309,637, 17,985,371 and 10,427,395 bytes. The 8 MiB reader stopped before subsequent usage. All inspected usage records had valid required counters; registering a version would not fix this.

The Codex reader now streams and validates complete non-usage response_item and world_state records up to 64 MiB without retaining their bodies. It validates the whole JSON object and UTF-8, including ignored strings, before advancing. Positional arrays cannot establish a native envelope. Each such record ends the scan window. Unknown types, usage records, malformed JSON, invalid UTF-8, missing newlines and records above the cap retain their held cursor/error. Cancellation and deadlines remain effective. Parser 8 automatically rechecks old positions and preserves parser 6’s complete-summary ownership correction. After a held line is completed and validated, its limit error no longer keeps file health degraded; earlier malformed-record errors and all diagnostics remain.

The initial parser-7 validation used a SQLite Online Backup including the live WAL. Only the independent statistics copy was written; a bounded native probe used normal Codex discovery filtered to the one affected file, with its original source read-only. Three bounded windows and one completion window reached EOF; the fifth scan was unchanged. The file became active_compat, without registering the client version. The other 563 Codex paths were not rescanned in this probe. It added 772 events and preserved all 10,025 prior events, including token/quality/model/ownership/cost, first observation and creation fields. Parser references and update bookkeeping were excluded from that comparison. Conflicts remained zero and the original line_too_long diagnostic remained.

An independent Python calculation compared native records through the committed byte offset, excluding newer concurrent appends. All 1,097 unique native calls matched the stored six counters: input 209,623,066; cache read 204,910,208; cache write 0; output 1,033,033; reasoning 454,809; total 210,656,099. Another 49 already collected session events absent from that retained stream remained in history.

The new integration test failed on the original reader because the post-output call was never imported. Final targeted checks pass: two streaming validation unit tests, six oversized-record integrations, five health/replay and nine 0.3.3 regressions. They cover both readers, old parser metadata/unchanged cursors, exact byte positions, repeat reads, unknown/usage/malformed types, invalid UTF-8, CRLF, escaped text, missing newlines, partial-line completion, array rejection, transactional rollback/reopen and the byte cap. Sanitized logs and probe code are under ignored build/codex-qoder-review/; the native statistics backup/WAL/SHM were removed after comparison. This is local parser/SQLite acceptance, without a rebuilt installed application, GUI/package lifecycle or other-platform acceptance.

Source-derived Qoder support

On 2026-10-22 the user confirmed that no Qoder client was installed and authorized source-derived synthetic data. Official distributions were downloaded/unpacked only; no installation scripts, client, login, hooks or model requests were run. This is compiled-distribution source inspection, not a claim that the full product is open source.

IDE/plugin negative fixtures prove rejection, not successful token support. All real-client and other-platform runtime acceptance remains pending.

The original 19-test M8 suite also passed with the new reader.

npm run check:docs checked 207 repository pairs and 21 guide pairs with no Astro findings; npm run test:docs passed 39 tests. A native-environment npm run build:docs produced 1,401 pages and checked 2,935 published files, local links, fragments, search, sitemap, language roots and publication markers. Pagefind similarly returned PermissionDenied in the sandbox and passed in the native build environment. Logs retain these first failures and subsequent results under build/codex-qoder-review/, including verify-qoder-final-4.log, qoder-tests-promoted-final.log and clippy-promoted-final.log.

The follow-up review reproduced Qoder’s long-prefix detection failure, stalled metadata/error-only first windows and filename-based exclusions. It also reproduced Codex accepting positional arrays as record objects. These checks failed before their fixes. Seven additional integration tests and expanded streaming unit assertions cover the repairs, rollback, SQLite reopen and unchanged old processing positions. Final npm run verify exited 0: 1,100 Rust tests passed, nine ignored; 20 script and 24 frontend tests passed, along with formatting, Clippy, types and frontend build. Logs are under build/review-codex-qoder/, including qoder-before.log, corrupt-before.log, codex-before.log and verify2.log. The first full verification stopped at workspace formatting; cargo fmt --all corrected the test files before the passing rerun. One new Codex integration initially expected a held-line result for an unlisted version that correctly returned incompatible; the fixture now uses a registered version to test the held cursor independently.

The installed collector was not rebuilt/upgraded, no statistics database was cleared, and no GUI, installer or real Qoder request acceptance is implied. Codex recovery runs when the rebuilt collector scans existing sources, potentially over several bounded windows.
