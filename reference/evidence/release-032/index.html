Version 0.3.2 compatibility and telemetry wording checks

Scope: repair Codex/Kilo compatibility notices using version-specific native samples, clarify the local OTel description and set application manifests to 0.3.2. The local checks below preceded tagging and remote CI; subsequent tagged-build results are recorded separately. Native source extraction is read-only and follows the redaction requirements.

Compatibility notices

The local application database contained 66 Codex files and one Kilo database marked active_compat. This notice means the reader recognizes the format while the owning client version remains unverified. It is separate from a record error. Codex versions 0.159.0-alpha.12.1, 0.160.0, 0.160.1 and 0.162.0-alpha.17.2 were missing from the registry. Kilo had 27 unregistered session versions, including 7.8.3 and 7.8.7. Earlier empty 7.8.3 sessions did not verify usage; the present native sessions contain actual calls.

Each added version has an independently extracted native sample and calculated expectations in tests/fixtures/{codex,kilo}/releases-032/ under the core crate:

Kilo’s 27 complete native sessions contain 787 assistant calls. Exact added versions: 7.3.42, 7.3.45, 7.3.46, 7.3.49, 7.3.50, 7.3.54, 7.3.63; 7.4.1, 7.4.2, 7.4.5, 7.4.7, 7.4.11, 7.4.13, 7.4.15, 7.4.16, 7.4.17, 7.4.20, 7.4.22, 7.4.23; 7.5.6, 7.5.14; 7.6.0, 7.6.2; 7.7.5, 7.7.12; 7.8.3, 7.8.7. The per-version expectations retain all five exclusive buckets, derived totals, missing reported totals and native session snapshots. Twenty-six snapshots match; 7.3.42 has a zero cumulative snapshot despite positive detailed usage. Its mismatch remains an audit diagnostic and is not used to discard valid calls or verify a version.

Bodies, paths and identifiers were removed or anonymized before samples entered Git. Provider identifiers in the new Kilo samples are replaced with a constant; model names, times, token numbers and the owning session version are retained. These samples verify the native CLI/database formats only, without extending IDE or telemetry support.

compatibility_release_032.rs creates genuine prior event hashes using fallback parsing references, consumes cursors, then reruns discovery through the complete built-in registry. It checks parent-directory discovery, each token field, known-version references, unchanged statistics/first observations, retained diagnostics, no conflicts and idempotent repeats. Unknown/missing versions, mixed databases, empty sessions and invalid rows retain their existing checks. Registering one version does not certify adjacent versions.

The real old-database check also exposed a file-continuity defect: a stable 63,974,896-byte Codex file repeatedly stopped at byte 33,554,261. The stored creation fingerprint differed from the file’s current creation time. A reread saved its size, modification time and content fingerprints but omitted the new creation time, causing another generation reset on every scan. The framework now saves creation time with the other fingerprints, events and cursors in the same transaction. An independent regression failed with one call instead of three before the fix; it now verifies one reset, progress after database reopening, all three calls and unchanged source bytes.

Creation-fingerprint regression coverage

Issue #1 identified a valid test gap: codex_file_fairness.rs returned before any assertions when the filesystem supplied no creation time. The test now always runs. With a native creation time it retains the recreated-file case; without one it seeds an old creation time and a mismatched prefix to force a rescan. After reopening SQLite it checks the complete persisted fingerprint, including clearing the stale creation time, and exactly one generation increment. It then checks all three calls/360 tokens, stable fingerprints/generation on repeat reads and unchanged source bytes. Product code and collection behavior are unchanged.

Follow-up validation on 2026-10-19 used Windows x64, Node 24.22.0 and Rust/Cargo 1.99.0 with locked dependencies. All four file-fairness tests passed both with native birthtime and with a temporary probe mutation returning created_ms = None. Temporarily removing row.created_ms = probe.created_ms made the repaired regression fail in both modes (exit 101): the persisted fingerprint retained the stale creation time. Both production files were restored before the final checks. The missing-birthtime run is a simulation; it does not establish Linux filesystem or remote CI acceptance. Logs and independent temporary databases are under ignored build/issue-1/.
