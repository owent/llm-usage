0.3.3 本地数据修复

日期：2026-10-19。应用、npm、Cargo、Tauri 版本统一为 0.3.3。依赖范围未变； pnpm 锁文件没有项目版本字段。本次处理三个报告的问题，使用只读本地 Agent 来源及独立统计库副本。 未改写原始 Agent 文件或正在使用的统计库，也未发起新的模型请求。

趋势：三条待核查记录

三条均为原生版本 0.163.0 的 Codex codex-rollout-5 记录。子线程 rollout 第二行 compacted.payload.latest_token_usage_record 携带了另一线程的响应。旧读取器将其归到 子线程，使用压缩时间且模型为空。所属线程包含同一响应 ID、完全相同的用量、原始时间及 codex-auto-review 模型。两处均被读取后产生三条归属/模型冲突。

记录 含缓存输入 缓存读取 输出 推理子集 总量
1 174,049 169,728 72 14 174,121
2 66,172 63,232 78 19 66,250
3 162,642 160,512 76 8 162,718

解析器 6 不再将外部线程的继承快照计为新调用。恢复要求从该快照重建的完整旧事件摘要匹配， 同时存在所属线程的原生响应，且用量、质量和修订一致。在事务内修正归属、模型和时间， 保留原始观测时间及诊断。不同的原生候选跨扫描窗口保存，后来的匹配记录不能抹去真实矛盾。

最终的一致性旧库副本初始有 11,208 条 Codex 事件、三条冲突。三轮读取处理了 136 个现存 源文件；第一轮在有界文件窗口处停止，第二轮完成。三条误报冲突降为零。全部原有事件仍存在； 八个 token 字段、质量、费用、创建时间及观测时间的变更数量均为零。 三条旧 update_conflict 诊断保留，另有三条 inherited_compaction_corrected。 扫描还从正在使用的本机会话采集了 240 条较新的 Codex 记录，与三条归属修正分列。

来源提示

初始数据库有 18 个 Codex 文件及一个 Kilo 文件标为 active_compat，来源健康正常。 预期记录结构完整且有效时，不再仅因版本未列入精确注册表而显示兼容标记。 内部版本、解析器依据及兼容诊断保留。坏记录、必需归属缺失及不支持格式仍显示具体提示。

“源文件已被清理”原先仅依据已登记路径不存在。初始快照有 354 个 Codex 路径和一个 VS Code Copilot 路径缺失，不能证明由哪个程序移动或删除。按用户要求，十种语言现均改为 “源文件已被清理或归档”。悬浮提示说明实际观察到的路径缺失， 不认定是 Agent 删除了文件；访问检查错误也不再被归类为路径缺失。 已采集历史仍遵循保留策略，缺失的原始文件及未采集内容无法重扫恢复。清空数据前应保留统计备份。

OpenCode v2

本机 2.0.32 数据库使用 session_v2 和 session_message，没有旧的 session/message/part 布局。旧读取器按规则拒绝了尚未核验的投影，产生“未识别 1 个文件”。 本次已依据官方 v2.0.32 的结构、写入器、归一化、分支及压缩代码实现独立读取器； 见源码依据与字段规则。

只读原生快照包含两个会话、15 条消息：七条 assistant、三条 user、三条 idle、一条 system、 一条 model-switch。七条已完成 assistant 各导入一次，使用自身模型/供应商及原生完成时间。 独立核对的原生求和如下：

字段 已知量
未缓存输入 78,811
缓存读取 93,632
